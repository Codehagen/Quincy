### Plan defects found during execution — a pattern worth knowing

Three of these plans shipped with a wrong `grep -c` / `grep -n` expected value.
The substance of every criterion held up; the arithmetic did not. The cause was
the same each time: the counts were written from what the prose was *intended*
to say rather than from running the command.

- **015** expected `grep -c "details-content"` to return 3. Real answer 7 — the
  doc comment mentions the pseudo-element three times in prose.
- **011** expected `grep -c "CRON_SECRET"` to return 2 ("once in the prose, once
  as the assignment"). Real answer 1 — `grep -c` counts matching *lines*, and
  the prose refers to the variable by pronoun, never by name.
- **012** expected `grep -n "JSON.parse(body"` to return no matches.
  Unsatisfiable by construction: the plan's own Step 1 names `idFromBody`'s
  parameter `body`, so its guarded internal parse always matches.

A fourth defect was structural rather than arithmetic. **017's guard legitimately
broke a pre-existing test.** The `X near expiry is not the user's errand` case in
`scripts/verify-channel-maintenance.ts` seeds an X connection five days from
expiry and asserts `active`. It had only ever passed by accident: a token five
days out is not stale, so `getAccessToken` returned without needing credentials.
The new guard runs first and correctly reports `unconfigured` on any machine with
no X app. The executor stopped rather than choose between three plausible repairs.

The fix was better than any of them: `config()` reads `process.env.X_CLIENT_ID`
at call time, so the script can *decide* whether X counts as configured instead
of depending on the machine. Step 4b now sets throwaway values with `??=` for the
refreshable case, and Step 4 deletes them for the unconfigured case. Both run
everywhere. That also repaired a hole in the original plan: Step 4's new case
self-skipped when X *was* configured, so on a machine with an X app the guard
would never have been exercised at all.

All three count defects were caught by executors that reported the discrepancy with evidence
instead of contorting the code to hit the number — which is the behaviour the
prompt asked for and the reason none of them shipped a bad change. **When
writing a done-criterion count, run the command first.** Prefer a check that
asserts a property ("the rule sits inside the reduce block") over one that
asserts an integer.

### Findings considered and rejected

- **Constant-time `CRON_SECRET` comparison.** High-entropy secret behind HTTP
  jitter; not a plausible timing oracle. Both routes already fail closed.
- **The `next` middleware-bypass advisory (Next 16.2.6).** Worth taking on the
  next bump, but `proxy.ts:13` says outright it "is not the gate" and
  `app/(app)/layout.tsx:39` does the real `getSession()` check.
- **CSRF Origin check on `/disconnect`.** better-auth's `sameSite: "lax"`
  default blocks the cross-site POST today. Defense-in-depth only.
- **Refresh-token race writing a terminal `revoked`.** Mechanism is real but
  depends on X returning `invalid_grant` for token reuse, unverifiable from the
  code. Needs measurement against a live X app, which does not exist yet.
- **`/privacy` rendering dynamically.** True, low value.
- **`lastError` carrying verbatim platform bodies into `toSafeConnection`.**
  Latent only — nothing renders it today.
- **`getAccessToken` returning the full row rather than a `SafeConnection`.**
  Guarantee-by-convention, not a live leak.
- **OAuth handshake not bound to the initiating session.** Narrow: needs a
  same-browser account switch mid-flow. The `state` cookie stops the
  cross-origin variant.
- **`<Link href="/api/connect/...">` being prefetched.** MED confidence; worth
  closing whenever that file is next touched.
- **`sharp` / `postcss` advisories.** Pre-existing, build-path only.

### Findings considered and rejected (timezone run)

- **`instantOf` mishandling readings near a transition**: not a finding. Probed
  all six days flanking both 2026 Europe/Oslo transitions; every one resolves
  correctly. It is *untested*, which is plan 008 — a different thing from wrong.
- **`parseDayKey` corrupting two-digit years**: not a finding. `Date.UTC` maps
  years 0–99 to 1900+, but the normalisation check in `parseDayKey` rejects the
  input before that can matter (`50 !== 1950`).
- **Unbounded growth of the `FORMATTERS` map in `lib/timezone.ts`**: not a
  finding. Keys are IANA zone names and invalid zones throw before being cached,
  so it is bounded by the ~600-entry zone set.
- **`TimeZoneSync` re-writing on every navigation**: over-reported, then
  disproved. App Router layouts do not remount on soft navigation, so it fires
  once per full page load. The user-visible half of that finding is real and is
  plan 005.
- **The `timestamp` → `timestamptz` migration shifting stored instants**: not a
  finding. Drizzle writes naive columns as `toISOString()` and reads them back
  with `+0000`, and the migration's `USING ... AT TIME ZONE 'UTC'` clause says
  so explicitly. Verified against the live database after applying.
- **Threading a zone into `lib/heartbeat.ts`**: not worth doing. The heartbeat
  compiles an inbox and has no wall-clock semantics, so there is nothing for a
  zone to change. The cron's fixed UTC schedule *does* matter, but only once a
  rhythm with a wall-clock promise ships — see "Deferred" below.

### Deferred, with reasons

- **No CI-runnable regression test that `getLineup` is host-zone independent.**
  The property is proven by `scripts/verify-timezone.ts`, which needs a live
  Neon connection and a seeded `dev@quincy.test`, so `pnpm test` cannot run it.
  Making it a unit test means separating `getLineup`'s day assembly from its
  query — a refactor of working code, which is a larger and riskier change than
  the four plans above. Worth doing when `lib/lineup.ts` is next opened for
  other reasons.
- **Changing a stored timezone reinterprets standing slots but not queued
  posts.** A slot is `weekday + "HH:MM"` with no zone, so it follows the user's
  current zone; a `scheduled_post` holds a fixed instant and does not. Both are
  correct in isolation and they diverge on a zone change. Latent today because
  nothing in the product can change a stored zone. **Whoever builds the settings
  surface must answer this before shipping it** — the honest options are to
  re-anchor queued posts to the new zone, to leave them and say so, or to refuse
  the change while anything is queued.
- **Publishing has no scheduler, and `vercel.json` has one weekly UTC cron.**
  `scheduled_post` has no create path outside the seed — only `movePost` — so
  "schedule this approved version" does not exist as a product action yet. Both
  gaps belong to `plans/005-connect-x-and-linkedin.md` (note: a different 005,
  in the other plans directory) and should be settled before its Phase 4.
- **`lib/rhythms.ts` promises per-user wall-clock timing the scheduler cannot
  keep.** Line 261 says "Sunday evening Quincy fills next week's slots" and line
  440 says "Monday morning, the week as one paragraph", both served by a single
  `17 22 * * 1` UTC cron. Nothing is broken today because the only rhythm that
  runs has no wall-clock meaning. The next one inherits the problem.

### Plan defects found during execution — a pattern worth knowing

Three of these plans shipped with a wrong `grep -c` / `grep -n` expected value.
The substance of every criterion held up; the arithmetic did not. The cause was
the same each time: the counts were written from what the prose was *intended*
to say rather than from running the command.

- **015** expected `grep -c "details-content"` to return 3. Real answer 7 — the
  doc comment mentions the pseudo-element three times in prose.
- **011** expected `grep -c "CRON_SECRET"` to return 2 ("once in the prose, once
  as the assignment"). Real answer 1 — `grep -c` counts matching *lines*, and
  the prose refers to the variable by pronoun, never by name.
- **012** expected `grep -n "JSON.parse(body"` to return no matches.
  Unsatisfiable by construction: the plan's own Step 1 names `idFromBody`'s
  parameter `body`, so its guarded internal parse always matches.

A fourth defect was structural rather than arithmetic. **017's guard legitimately
broke a pre-existing test.** The `X near expiry is not the user's errand` case in
`scripts/verify-channel-maintenance.ts` seeds an X connection five days from
expiry and asserts `active`. It had only ever passed by accident: a token five
days out is not stale, so `getAccessToken` returned without needing credentials.
The new guard runs first and correctly reports `unconfigured` on any machine with
no X app. The executor stopped rather than choose between three plausible repairs.

The fix was better than any of them: `config()` reads `process.env.X_CLIENT_ID`
at call time, so the script can *decide* whether X counts as configured instead
of depending on the machine. Step 4b now sets throwaway values with `??=` for the
refreshable case, and Step 4 deletes them for the unconfigured case. Both run
everywhere. That also repaired a hole in the original plan: Step 4's new case
self-skipped when X *was* configured, so on a machine with an X app the guard
would never have been exercised at all.

All three count defects were caught by executors that reported the discrepancy with evidence
instead of contorting the code to hit the number — which is the behaviour the
prompt asked for and the reason none of them shipped a bad change. **When
writing a done-criterion count, run the command first.** Prefer a check that
asserts a property ("the rule sits inside the reduce block") over one that
asserts an integer.

### Why 018 is the one to do first

Approving a draft after the slot time on a slot day schedules it into the past.
The sweep then either publishes it within five minutes — the user was told
"going out Monday 08:00" and it goes out at 09:34 — or, past the two-hour
catch-up window, marks it failed. With one slot per channel, which is the shape
the product is designed around, this hits anyone who approves in the afternoon.

### Findings considered and rejected

- **`unschedulePost` and `movePost` have no state guard** (`app/(app)/lineup/actions.ts`).

  hides the controls, and there is no cross-user exposure. Worth a one-line
  `inArray` guard matching the one `reopenVersion` already has, next time either
  file is opened.
- **Claim concurrency is asserted but never raced.** `scripts/verify-publish-run.ts`
  proves a `sending` row is not re-selected, but every call in it is sequential.

- **`deleteSlot` has no UI.** The server action exists and is correct; nothing

### Direction — options, not defects (the owner's call)

- **Depth has no code.** `docs/vision.md` calls converting attention into
  people "what Quincy is actually for" and weights Depth above Volume; the
  shipped product is Volume end to end (adapt → rhythms → publish) plus a
  Numbers page. There is no reply drafting, no inbound mentions, no entity
  for a person who keeps showing up. The narrow spike: X mentions on your
  own posts, metered like the corpus read, drafted into the Riffs shape,
  sent by hand. The risk to hold structurally: a reply surface is one
  careless default from autoposting, which vision.md forbids.
- **`sending`/`failed` posts have no operator surface.** Seven publish
  outcomes, UI actions for one. `countUnresolved()` goes only to a cron
  JSON body. A `requeue` (from `failed`) and a human `resolve` (from
  `sending` — "it published, here is the URL" / "nothing sent, requeue")
  on the existing lineup row closes every dead end. The `unconfirmed` case
  must stay a human assertion, never a retry button.
- **Turn the shipped-work pipeline on this repo before filming video 01.**
  The GitHub App, selection pass and riff pipeline exist and are owed a
  real merge anyway (plan 021's record); the video's own claim — "a
  receipt, not a roadmap" — is strongest if the changelog entry in the
  film was drafted by the pipeline from a real merge.
- **Decide what Cuts is.** A third of the codebase, the busiest area by
  churn, absent from `docs/vision.md`'s surface table; its agent does not
  read the brain. One written row settles whether cuts arrive in the
  Lineup as publishable artefacts or the boundary is cut deliberately.
- **The trial ceiling should be cost-based, not a turn counter.**
  `docs/billing.md`'s `trialTurnsUsed` premise is stale —
  `summariseUsage` already aggregates `costMicros` per user in one query.
  Plan 030 ships that mechanism generically; plans/008 in the other
  directory becomes "set the number from two weeks of data".
